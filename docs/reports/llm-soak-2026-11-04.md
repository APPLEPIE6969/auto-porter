(chunkcourier's `PlayerTickEvent` → `player_tick`, the pure-LLM path) was
pushed through real NVIDIA NIM generation **100 times per round**, twice —
once on the old prompt (baseline), once after the fixes. Every raw
request/response pair was captured via `AUTO_PORTER_LLM_TRACE` and autopsied
with `scripts/analyze_soak.py`.

## Round-1 autopsy — why the model failed 100/100

Inspecting the captured prompts showed the model was behaving rationally;
the inputs were the problem. Three root causes:

1. **No signature existed in the prompt.** The "AVAILABLE HOOK SIGNATURE"
   section carried only catalog metadata (name, contract, version, target) —
   no Rust code — while the system contract simultaneously demanded
   "match the provided hook signature exactly".
2. **The contract the few-shot taught was factually wrong.** Horizon's real
   generated trait at the pinned revision is
   `fn player_tick(&self, host: &mut dyn Host, event: &mut PlayerTickEvent)`,
   with cancellation expressed by returning `Flow::Cancel` — the templates
   taught `fn {{HOOK_NAME}}(&mut self)` and out-parameter cancellation, which
   the 5 code attempts dutifully reproduced and the offline signature check
   rejected (`wrong_shape` × 5).
3. **No Java behaviour was visible.** `JAVA BEHAVIOUR` was a single decompiled
   descriptor line (`...onPlayerTick(...)V (has_code: true)`); with no body to
   port and no usable signature, the model's honest answer was the sentinel —
   95 times out of 100.

Infra noise (25 × HTTP 429, 7 × 180 s timeouts) was absorbed by the retry
loop and is excluded from the correctness accounting.

## Fixes shipped between the rounds

- `2d9dc1b` — prompt v2: real `HOOK CONTRACT` with the exact Rust signature
  and Horizon's own doc text, `Flow` semantics, real-shape few-shot
  (`item_picked_up` with `Flow::Cancel`); **signature-enforcing validator** so
  `ported` can no longer mean "anything brace-balanced";
  `hooks/hook-signatures.json` extracted from Horizon's pinned sources
  (384/386 hooks, 126 helper signatures, all event structs; extractor:
  `scripts/extract-hook-signatures.py`)
- `897f783` — fixture's real upstream Java sources committed and fed via
  `--source` in the CI smoke and the soak (the model now sees the actual
  behaviour it must replicate); per-run trace files

## Round-2 notes

- 84/100 runs succeeded on their first call; the 16 remaining runs needed
  extra calls, but **every one of those was an infra retry** (429 backoff or
  timeout) — all 100 code-producing model responses were accepted as-is, so
  the self-repair loop never had to engage.
- Spot-verified APIs in generated code (`host.acting_player()`,
  `host.tell(uuid, Text::literal(...))`, `AtomicU32` interior mutability on a
  `&self` receiver) are real Horizon APIs; zero invented identifiers across
  all 100 generations.
- p50 latency rose from 33 s to 85 s: prompt v2 carries the signature table,
  hook docs and the full Java source (~4.3 k prompt tokens vs ~1.3 k). That
  is the deliberate price of correctness.
- Residual variance is exclusively free-tier 429s; the retry budget (100
  attempts, 1 s backoff, 60 s per call — plus the 180 s envelope) absorbed
  all of it.

## Remaining gap

Generated modules now match the real `mod_api::Hooks` contract, but the
`.hnmod` packaging (`[api]` / `trait_method` / `bindings` glue in the
launcher's format) is still template-shaped — see `docs/limitations.md`
§8 "Bundle bindability" for the open workstream.
